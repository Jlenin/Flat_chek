# Архитектура flat_check_modular

Этот документ — карта того, что откуда грузится и почему. Если нужно найти
код конкретной проверки/флага — смотрите таблицу «Где что искать» в конце.

## Зачем это отдельная версия

`flat_check.sh` (health, 3.8.10) и `flat_check_2.sh` (health + сборщик логов,
3.11.10) — два почти-дублирующих файла на 3300 и 9000+ строк, которые нужно
было держать в ручном «паритете»: любое исправление приходилось вносить в
2-3 места одинаковым патчем. Это была причина почти всех багов, найденных
перед началом этой работы (см. `CONTEXT.md` в корне репозитория).

`flat_check_modular/` — тот же функционал (health check + JSON/push-агент +
сборщик логов + интерактивный мастер), но с одним источником истины на
функцию, разложенным на три слоя. Оригиналы (`flat_check.sh`,
`flat_check_2.sh`, `agent/`) не менялись и продолжают работать как раньше —
это две параллельные, независимые поставки одного и того же инструмента.

Интерфейс командной строки (все флаги: `-h`, `-i`, `-r`, `-v`, `--json`,
`--push`, `--config`, `--dev`, `--selftest`, `-log -on/-off` и т.д.) не
менялся ни на один флаг — см. `lib/core.sh`, раздел `09_argv`. Что
изменилось — это только то, из скольких файлов собран код и как он
подключается.

## Три слоя + точка входа

```
┌─────────────────────────────────────────────────────────────┐
│  flat_check  (точка входа)                                  │
│  парсит argv → решает, что из lib/ подключить → диспетчер   │
└───────────────┬───────────────────┬──────────────────┬──────┘
                │                    │                  │
                ▼                    ▼                  ▼
        lib/core.sh (всегда)  lib/agent.sh (если   lib/logging.sh (если
        health-check,         --json/--push/       -log/-i/--dev/
        каталог пакетов,      --config/--dev/      --selftest/
        вывод, i18n,          --selftest/-i)       --list-targets)
        argv, мастер,
        selftest
```

| Слой | Файл | Когда грузится | От чего зависит | Кто от него зависит |
|------|------|-----------------|------------------|----------------------|
| core | `lib/core.sh` | всегда | ничего (кроме bash/coreutils) | agent и logging — оба |
| agent | `lib/agent.sh` | `--json` / `--push` / `--config` / `--dev` / любой `--selftest` / `-i` | только core | никто |
| logging | `lib/logging.sh` | `-log` / `-i` / `--dev` / любой `--selftest` / `--list-targets` | только core | никто |

**Циклов нет.** agent и logging не знают друг о друге и не вызывают функции
друг друга — это проверено `grep`'ом по фактическим вызовам функций между
секциями в оригиналах, а не только по комментариям. core не знает ни об
agent, ни о logging.

### Почему каждый файл — не один модуль, а несколько «разделов» внутри

Изначально (фазы 1-3) каждый слой был отдельной папкой из 3-12 файлов по
одной функциональной группе на файл (`00_globals.sh`, `01_catalog.sh`, …).
После код-ревью (фаза 5) это признано избыточной дробностью: 33 файла на
проект — слишком много, чтобы держать в голове, где что лежит, даже если
каждый файл сам по себе невелик. Слои (core/agent/logging) — это реальная,
осмысленная граница подключения по флагам, которую важно сохранить. Деление
*внутри* слоя на 3-12 файлов такой границей не было — это просто было
удобно при переносе кода из монолитов.

Поэтому теперь **один файл на слой** (`lib/core.sh`, `lib/agent.sh`,
`lib/logging.sh`), а прежние файлы стали разделами внутри — ищите по
комментарию `# РАЗДЕЛ: <имя>` (например, `grep -n "РАЗДЕЛ:" lib/core.sh`
покажет все разделы и их номера строк). Каждый раздел начинается с того же
заголовка-документации, что раньше был в отдельном файле (Назначение /
Публичные функции / Зависит от / Не зависит от / Side effects / Источник) —
информация не потерялась, изменилась только физическая упаковка.

### Почему `--selftest`/`--dev`/`-i`/`--list-targets` грузят ОБА опциональных слоя

Самотест — это проверка целостности всей ПОСТАВКИ, а не только того режима,
с которым его запустили: `lib/core.sh` (раздел `11_selftest`) на уровне
`simple` уже проверяет, что `build_health_json`/`push_health_json`
определены (agent), а на уровне `extended` дополнительно гоняет
`parse_duration`/seek+chunk extract (logging). Если бы `--selftest simple`
не подключал agent, он не смог бы даже сообщить, что agent вообще на месте.

Мастер (`-i`) устроен аналогично: сам мастер решает уже ПОСЛЕ старта, в
какой режим идти (health / сбор логов / самотест) — если бы agent/logging
подключались по флагам ДО входа в мастер, часть его пунктов меню осталась
бы без нужных функций.

`--list-targets` требует logging даже без `-log`: диспетчер вызывает
`list_log_targets()` по одному этому флагу (найдено при код-ревью фазы 5).

## Точка входа: `flat_check`

Псевдокод (реальный файл см. `flat_check` в этой же папке):

```bash
SCRIPT_DIR=... ; LIB_DIR="$SCRIPT_DIR/lib"

source "$LIB_DIR/core.sh"      # всегда

parse_args "$@"                # только разбирает флаги, ничего не запускает

# по разобранным флагам решаем, что ещё подключить
[[ ...-log/-i/--dev/--selftest/--list-targets... ]] && source "$LIB_DIR/logging.sh"
[[ ...--json/--push/--config/--dev/--selftest/-i... ]] && source "$LIB_DIR/agent.sh"

dispatch_main "$@"  # тонкий диспетчер: -i / --selftest / --dev / --json|--push / -log / health по умолчанию
```

Никакой динамической магии: ни `eval`, ни автозагрузчиков по имени функции,
ни реестров плагинов — обычный `source` и `if` по уже распарсенным флагам.

`SCRIPT_DIR`/`SCRIPT_NAME` вычисляются **в самой точке входа**, а не в
`lib/core.sh` — если бы это делал lib-файл, `${BASH_SOURCE[0]}` указывал бы
на путь этого lib-файла, а не на `flat_check`.

## Права на исполнение (`chmod +x`)

Только 4 файла верхнего уровня когда-либо запускаются напрямую: `flat_check`,
`install.sh`, `reinstall.sh`, `uninstall.sh`. Всё в `lib/*.sh` только
подключается через `source` — **исполняемый бит им не нужен в принципе**.
Самопочинка `+x` (тот же приём, что в `agent/install_flat_check.sh`)
встроена во все четыре верхнеуровневых скрипта: после первого ручного
`chmod +x install.sh` (или запуска как `bash install.sh`) остальное чинится
само при каждом install/reinstall/uninstall.

## Где что искать

Внутри каждого файла разделы идут в этом же порядке — искать по `grep -n
"РАЗДЕЛ:" lib/<файл>.sh` или просто открыть файл и полистать (`Ctrl+F`).

## Каталог пакетов и зависимости — не трогать бездумно

`conf/flat_check.packages.conf` — копия каталога продуктов/пакетов из корня
репозитория, скопирована как есть. Это данные (`_pkg_set` + `PKG_DEPS`), а
не код — при любых изменениях в этом файле сохраняйте существующие связи
«пакет → продукт → зависимости»; новые записи добавлять можно, существующие
менять — только осознанно и с пониманием, что от них зависит текстовый
`=== Depends ===` и JSON `"infrastructure"`.

## Обнаруженные расхождения между `flat_check.sh`/`flat_check_2.sh`/`agent/json_report.inc.sh`

Оригиналы не редактировались в рамках этой работы, но при построчной сверке
модульной сборки с ними нашлись места, где копии разошлись (естественный
результат ручного «паритета» несколькими патчами). В модульную сборку взята
исправленная/более полная версия в каждом случае:

1. `agent/json_report.inc.sh` не пропускал инфраструктурные пакеты
   (nginx/postgresql/mariadb) через `_is_infrastructure_pkg()` в блоке
   `directories` — показывал бы выдуманные пути `/opt/flat/<pkg>` со
   статусом `"missing"` вместо `"n/a"`. См. `lib/agent.sh`, раздел `02_json_build`.
2. `flat_check.sh` не звал `cleanup()` из `die()` — в режиме `-log` фатальная
   ошибка оставляла бы недоделанный рабочий каталог. См. `lib/core.sh`, раздел `02_output`.
3. `relocate_log_to_workdir()` в `flat_check.sh` отсутствует вовсе (health-only
   скрипт не создаёт рабочий каталог архива). См. `lib/logging.sh`, раздел `08_online_offline`.

Это находки для отдельных тикетов на сами оригиналы — они умышленно не
трогались в рамках декомпозиции (см. README.md в корне репозитория).

## Найденные и исправленные баги самой декомпозиции (фаза 5, код-ревью)

В отличие от находок выше, эти три — не расхождения оригиналов, а баги,
которые внесла сама декомпозиция (при переносе кода в модули; в оригиналах
их нет):

1. `--list-targets` без `-log` падал `command not found` — logging не
   подключался. Точка входа теперь считает `--list-targets` поводом
   подключить `lib/logging.sh`.
2. `lib/logging.sh` (раздел `07_collector`) дублировал байт-в-байт 6 функций
   resource-gate, уже существующих в `lib/core.sh` (раздел `06_resource_gate`) —
   попали туда при переносе секции целиком из `flat_check_2.sh`. Удалены.
3. `_collector_should_stop()` была продублирована с РАЗНЫМ телом — заглушка
   в core (`return 1`) и настоящая проверка Ctrl+C/timeout в logging.
   Работало по факту (core грузится раньше logging → logging побеждает), но
   не по документированному замыслу. Теперь единственное намеренное
   переопределение функции между слоями во всём проекте, явно
   прокомментированное в обоих местах.

## Проверка эквивалентности при дальнейших правках

1. `bash -n` на изменённый файл и на `flat_check`.
2. `./flat_check --selftest extended` — должен пройти без `[FAIL]`.
3. Сравнить вывод с оригиналом на одном и том же состоянии хоста:
   - `./flat_check_modular/flat_check --json` vs `./flat_check.sh --json`
     (сравнивать по ключам, кроме заведомо переменных — `timestamp`,
     `system.cpu`, `system.memory`, `system.uptime_seconds`, `certificates`);
   - обычный текстовый вывод — построчно;
   - `-log -off` на одном и том же наборе логов — список файлов в архиве.
4. Проверить, что функции нигде не задублировались случайно:
   `grep -rhoE "^[a-zA-Z_][a-zA-Z0-9_]*\(\)" lib/ | sort | uniq -c | sort -rn`
   — не должно быть строк с count>1, кроме документированного
   `_collector_should_stop` (см. выше).
